# **「AI 的 1968 时刻」** — 当"好"再次难定义

> 1968 年，人们问“怎么证明软件是对的”，答案是一个测试。2026 年，人们问"怎么证明模型是好的"，答案是一张排行榜。

小帅是一位大模型应用工程师。早晨到工位，他同时面对两个世界的荒诞。楼上的基模团队的小美发了技术报告，新模型 MMLU 89.7，登顶。同一天，竞对在 HumanEval 上宣布反超。第三家不参与这两个榜，挑了个自己赢的评测，配着火箭 emoji 说"全面领先"。三家都说自己是第一，三张图都无可辩驳。评论区有人问"所以到底谁更好用"，没人回答。

他自己的屏幕上，昨晚改的那版 prompt 让“指令遵循”涨了 1.4 分，“创造性”掉了 0.8。他不确定这算进步还是退步。中午跟算法同事争论 judge model 的校准是不是偏了——那个用来打分的模型本身，也是另一个不确定系统。下午翻用户日志，看到一条 case：用户让 agent 帮忙写一封拒绝合作的邮件，agent 写了，措辞得体，逻辑通顺，但用户追了一句"太客气了，我要让他知道我不高兴"。他盯着屏幕，不知道该改 prompt、改检索、还是改工具编排。

两个世界，同一个沉默。楼上不知道“模型好”长什么样，只能用一张自己挑的榜单回答。楼下不知道"这次改动是不是变好了"，只能用一组自己设计的分数安慰自己。没有人知道下一步该往哪走。

这不是因为这代人不够聪明。它暴露的是一个更古老的困境：当产出不再是"对或错"而是"好或不够好"时，方向感从哪来？上一次整个行业集体陷入这种焦虑，是 1968 年，联邦德国一个叫 Garmisch 的小镇。北约把几十位计算机科学家关在一起，试图回答一个当时同样令人窒息的问题：为什么我们突然不会写软件了？

## 1968：命名时刻

1968 年 10 月，北约科学委员会出钱，把大约五十位计算机科学家请到了巴伐利亚阿尔卑斯山脚下的 Garmisch-Partenkirchen。会议的组织者之一 Friedrich Bauer 后来回忆，选这个地方是因为“我们需要一个足够安静的地方，来承认一件令人难堪的事”。

那件难堪的事是：我们突然不会写软件了。

这不是修辞。1950 年代到 1960 年代中期，晶体管到集成电路的跃迁让硬件能力近乎指数增长。人们第一次有能力（也有预算）去构想真正庞大的软件系统——操作系统、防空网络、航天控制、银行核心。但写软件的方式还停留在“手艺人”阶段：一个聪明程序员，凭个人能力和直觉，从需求到代码一气呵成，没有规范、没有分工、没有验证机制。系统规模从几千行膨胀到几十万、上百万行时，人脑的工作记忆彻底兜不住。

IBM OS/360（1963–1966）是最经典的案例。投入超过五千人年，严重超期超预算，交付时 bug 密度极高，维护成本失控。Fred Brooks 把这段经历写成《人月神话》。同期还有美国空军 SAGE 防空系统、NASA 阿波罗飞行控制软件、英国政府多个信息化项目——到处是同样的故事：预算失控、进度崩塌、交付物没人敢碰第二遍。

![image-20260726183245718](/Users/yangliu/Library/Application Support/typora-user-images/image-20260726183245718.png)

Garmisch 会议给这个现象命名——"Software Crisis"。核心诊断是：问题不在于程序员水平不行，而是一个结构性矛盾——软件是纯逻辑构造物，没有物理定律帮你兜底（建筑有材料力学，电路有基尔霍夫），复杂度可以无限膨胀，而人脑容量固定。当系统超出单人可理解范围、又没有机制把正确性分而治之时，崩溃是必然的。

但 Garmisch 真正重要的不是诊断，是处方的性质。会议开出的药方不是某项技术突破，而是一整套纪律：结构化编程、模块化设计、形式化方法、独立测试。这些加在一起，后来有了一个名字——软件工程。它不是一项发明，而是一门学科。它让几百万人有了共同的语言、共同的方法、共同的职业自觉。

最朴素的信念是：你需要一个外在于代码本身的、可执行的判据，来告诉你"这一步走对了没有"。这个判据，最终凝结为"测试"。

## TDD：红灯变绿就是方向

从 1970 年代的结构化测试，到 1990 年代末 Kent Beck 把 TDD 正式化（Red → Green → Refactor），"一个会失败的测试"成为软件迭代最可靠的牵引力。

1999 年，Kent Beck 出版了《Extreme Programming Explained》，把一种已经在小圈子里流传的实践正式命名为 Test-Driven Development。规则只有三条：先写一个会失败的测试（Red），写最少的代码让它通过（Green），重构（Refactor）。循环往复。

![image-20260726183344441](/Users/yangliu/Library/Application Support/typora-user-images/image-20260726183344441.png)

这看起来只是"测试前置"，一个工程习惯的调整。但它真正做的事情比这深得多。它迫使你在写任何实现之前，回答一个问题：我到底要什么？而且这个回答不能是自然语言的、含糊的、"你懂我意思吧"式的，它必须是一段可执行的、无歧义的、机器能判定真假的断言。如果你写不出这个断言，说明你还没想清楚。测试不是验证工具，是思考工具。

这就是 TDD 作为牵引力的本质。反馈信号是确定性的、即时的、二值的。红或绿，过或不过，不需要讨论，不需要投票，不需要等三天后看数据报表。迭代的原子单位是"一个测试从红变绿"。这给了开发者一种在混沌中建立秩序的节奏感——你不需要理解整个系统，你只需要让眼前这一个断言从红变绿，然后下一个，再下一个。

Beck 自己说过，TDD 的核心价值与其说是保证质量，不如说是管理恐惧。软件项目里最大的恐惧不是“写不出来”，而是“不敢改”。一个运行了三年的系统，没人知道改一行会不会在某个角落引发雪崩。TDD 的回应是：你改吧，任何回归都会被立刻捕获。红灯亮了，就是你改坏了，改回去或者修好它。恐惧被消解为一系列小的、可处理的、确定性的信号。

小帅如果活在这个时代，他的工作会很单纯。改一个排序函数，跑测试，红了，修，绿了，提交。他不需要怀疑"什么叫对"——测试已经告诉他了。他的方向感是完整的：红灯就是方向，绿灯就是终点。

这套体系被工业化推到的顶点，是微软。1990 年代到 2010 年代初，微软的开发和测试比例接近一比一。每一个 SDE 旁边坐着一个 SDET，职级对等，薪酬对等，有独立的晋升通道。SDET 不是手工点点点的质检员，而是写测试框架、建自动化工具、设计回归策略的工程师。配套制度也很硬：谁提交的代码打破了构建，谁立刻停下手头工作去修；发布前所有已知 bug 必须清零或显式 defer。Windows、Office、SQL Server，这些产品的稳定性很大程度上是这套制度喂出来的。

2014 年，微软关闭了 SDET 职级，合并为统一的 Software Engineer。表面原因是 DevOps 和持续交付让串行交接变得笨重。更深的原因是：测试能告诉你“这个函数在输入 X 时没有崩溃”，没法告诉你“用户拿到这个界面时会不会觉得难用”。Google 走得更彻底——从一开始就没有独立测试岗。James Whittaker 在《How Google Tests Software》里写得很直白：你配一个人专门找你的 bug，你写代码时就会下意识放松。

回头看，这是一个信号：测试作为牵引力，天花板到了。不是它不好用了，而是它适用的问题域不再覆盖软件的全部。

TDD 有一个前提假设：正确性是可以被形式化规约的。排序算法、状态机、协议解析——这些你能写一个 assert，过了就是对了。但当你面对的问题变成“排序结果好不好”“推荐列表用户会不会点”“这段回答用户读了会不会满意”时，你写不出那个 assert。“好”不是一个布尔值。

红灯变绿，不再是方向。

但注意，在 TDD 的世界里，有一个问题从来不需要被回答：谁来决定这个 assert 该写什么？答案是不言自明的——写需求的人，签合同的人，坐在你对面告诉你“我要一个能按日期排序的列表”的那个人。定义权从来没有悬空过。它属于一个具体的、可指认的、会为后果负责的人。

这个确定性，是 TDD 时代最不被珍惜、也最先消失的东西。


## 搜索：几百页手册

互联网用不到十年时间，把“用户”这个词的含义彻底改写了。

1995 年，你写一个软件，用户是坐在你对面的那个人。他叫什么名字，在哪个部门，要什么功能，你清清楚楚。他不满，会直接走到你工位旁边拍桌子。2005 年，你写一个搜索系统，用户是一千万个你永远不会见到的人。他们不会拍你的桌子。他们只是搜了一下，没找到想要的东西，然后关掉了页面。你甚至不知道他来过。
![image-20260726183357982](/Users/yangliu/Library/Application Support/typora-user-images/image-20260726183357982.png)

这是搜索面对的第一个新问题：反馈消失了。传统软件里，用户不满意会投诉、会提工单、会拒绝验收。搜索里，用户不满意只是离开。沉默的、不可归因的、大规模的离开。你面对几亿人，但你听不见任何一个人的声音。

第二个问题紧跟着来：你服务的人太多了，多到你没法跟他们对齐“好”是什么意思。传统软件里，“好”是合同里写好的那几条。搜索里，几亿人各有各的搜法，各有各的期待。你不可能跟每个人谈一次。你必须替他们所有人决定：什么样的结果算好。

但有一个前提还没有被打破：所有用户被当作一个整体来服务。搜“北京天气”的一千万人，拿到的是同一组结果。用户之间的差异在那个阶段还不重要。重要的是：对于每一种类型的需求，存在一个统一的、所有人都适用的“好”的标准。

于是问题变成了：你能不能把这个标准写出来？

他们写了。几百页的评测文档，每一种需求类型对应什么样的结果算好、什么算差、什么算勉强及格，逐条列清。评估员不需要有品味，不需要有直觉，他需要的是耐心和服从——找到对应条目，对照结果，打分。个人判断被压缩到接近于零。

围绕这套文档，一支规模不小的专家团队运转起来。他们不写算法，不碰代码，每天对着屏幕上的搜索结果一条一条地判。判完了，分数汇成报表，算法团队看报表决定改什么。改完了，再送回来判。如此循环。日复一日。

它确实管用。搜索在这个循环里肉眼可见地变好——垃圾结果少了，答非所问少了，你想找的东西越来越在前几条就能出现。几百页手册是法律，几百号评估员是法官，算法是那个不断被传唤、不断被纠正的被告。牵引力明确而稳定：专家说不好，你就改，改到说好为止。

但搜索团队里不只有评估员。还有另一拨人，盯的是用户行为。点击率、停留时长、二次搜索率——几十亿次点击，每天都在投票。数据派的主张很朴素：用户觉得好就会点，觉得不好就会走。

这两拨人之间的冲突是结构性的。算法团队拿着数据来申请上线：点击率涨了三个点。评测团队拉出来看：涨的那三个点，是标题党贡献的。用户点了，三秒退出，换个词重新搜。数据说赢了，评测说输了。

反过来也一样。评测团队判定质量提升——来源更权威，垃圾结果被压下去了。上线一周，点击率跌了。用户就是更想点那条耸动的结果。评测说赢了，数据说输了。

每一次都是这样。双方手里都有证据，但没有一个更高的标准来裁定谁的有效。在早期搜索里，这场仗最终是人工评测赢了。逻辑是：搜索是基础设施，用户行为里噪声太多，不能让噪声定义质量，而应该让更懂搜索（也可能没那么懂用户）的人来定义“好”。数据派退到辅助位，最终签字的是评测团队。

小帅如果活在这个时代，他不再修 bug 了。系统没有崩溃，没有报错。他的工作是改一版排序策略，送评测，等分数。涨了就上线，没涨就接着调。方向感还在，但不是他自己的——是那几百页文档给他的。

但事情也在发生变化。互联网正在长出搜索框以外的形态。用户不再总是带着一个明确的问题来，越来越多的时候，他只是在刷，在逛，在消磨时间。他没有输入任何词，也就没有给你一个可以评判的意图。那几百页手册，开始找不到落笔的地方。

## 推荐：用户自己投票

2012 年前后，移动互联网把互联网的用户规模又推上了一个量级。智能手机让上网不再需要坐在电脑前，三四线城市、县城、乡镇的人涌了进来。他们不是五环内的互联网从业者，不是评测专家能够代入的那种用户。他们刷手机的方式、想看的内容、对"好"的感受，跟那几百页手册背后假设的人群，已经不是同一拨人了。
![image-20260726183407707](/Users/yangliu/Library/Application Support/typora-user-images/image-20260726183407707.png)


与此同时，商业竞争的核心指标变了。不再是“搜索结果准不准”，而是 DAU、时长、留存。用户每天打开手机的时间是有限的，所有产品都在抢。在这个战场上，“专家觉得好”没有意义，“用户愿意留下来”才有意义。一个评测分数再高，如果用户刷了三十秒就关掉 app 去了别家，这个分数就是废纸。

旧的那套评测方法开始掉队。不是它错了，是它慢。几百页手册的更新速度跟不上产品迭代的速度，评测专家的判断覆盖不了几亿下沉用户的偏好多样性。而数据驱动的增长体系，天然就是为这个速度设计的：上线一个策略，跑一天数据，看指标动没动，动了就留，没动就撤。不需要等评测团队排期，不需要翻手册找条目。

数据派也不是没有遇到过问题。标题党 hack 了点击率，那就加一个“有效阅读时长”的指标。用户点了就退出来骗了停留时长，那就看"完播率"。指标被攻破，就修指标，修完了接着跑。这是一个可以自我修复的体系——你不需要一个几百页的文档来穷举什么是好，你只需要一个能不断逼近"用户真正满足"的北极星指标，然后在它被污染时迭代它。

移动互联网之后成长起来的公司是这套逻辑走到极致的产物。比如某个国民级短视频 APP ，产品做的事情，本质上就是设计一切交互来采集用户反馈——每一次滑动、每一次停留、每一次点赞或划走，都是一个信号。算法做的事情，是建模这些信号，预测用户行为，最终优化用户的整体满意度。产品和算法不是两个团队在交接，而是同一个循环的两半：产品制造数据，算法消费数据，算法的输出又变成产品的新输入，如此双向奔赴。

在这个体系里，没有评测专家的位置。或者说，专家的角色从裁判变成了指标的设计者和校准者——他不判每一条结果好不好，他判的是"用什么尺子量"。尺子定好了，剩下的事交给数据。

小帅如果活在这个时代，他的方向感来源又变了。不是几百页文档，不是一群专家的判断，是一个数字。一个被反复校准过的、被认为能代表用户满足的数字。他每天盯着它，它涨他就对了，它跌他就错了。方向感回来了，但它的来源是一个统计量，不是一个人。

回头看一下。

从测试到评测手册到用户行为指标，表面上是方法论在迭代。但真正在转移的是定义权——谁有资格说"这就是好"。

而定义权从来不是一个抽象的哲学问题。它的归属取决于一个更朴素的事实：谁付钱。

软件时代，客户付钱。他坐在你对面，合同里写好了验收标准，他说好就是好。搜索时代，广告商付钱。广告商要的是搜索次数——用户搜得越多，广告展示越多，收入越高。所以"好"约等于"让用户愿意继续搜"。推荐时代，还是广告商付钱，但要的东西变了：DAU，时长。用户留得越久，广告位越多。所以"好"约等于"让用户愿意继续刷"。

你看到了：在搜索和推荐时代，"用户满意"这四个字背后站着的，是收入。用户满意意味着他还会来，还会留，还会产生更多的广告展示。专家也好，数据也好，最终都是在为这个商业等式服务。定义权看起来在专家手里、在用户行为里，但归根结底，在付钱的人那里。

这个等式运转了几十年，没有人觉得有问题。直到大模型来了。

## AI：工具过剩，权威真空

2022 年底，ChatGPT 上线，两个月一亿用户。此后三年，大模型不断给出惊喜：能写代码了，能看图了，能操作电脑了。没有人怀疑它的价值。驱动这些进步的迭代体系，本身也是一件真实的工程成就——三年之间，模型从"能对话"进化到"能执行任务"，这个速度在软件史上没有先例。

早期训练大模型的核心思路是 RLHF：不定义“好是什么”，只问“A 与 B 孰优”。你不需要回答一个哲学问题，只需要完成一次比较。几十万条人类偏好对比，训练出一个奖励模型，模型朝人类更偏好的方向收敛。这个策略绕开了"定义好"的难题，将牵引力从一个标准降格为一次比较。它奏效了。ChatGPT 即是证明。
![image-20260726183415144](/Users/yangliu/Library/Application Support/typora-user-images/image-20260726183415144.png)


但它奏效有一个前提：比较的语境是收敛的。早期 RLHF 面对的场景极为单一——一个用户提出一个问题，模型给出一个回答，标注员判断哪个回答更有帮助。“有帮助” 在这个狭小的语境里是有共识的。你不需要几百页手册，不需要北极星指标，只需要一个正常人的直觉。

这个共识正在瓦解。

大模型不再只是“回答一个问题”了。它写代码、做翻译、当客服、陪聊天、操作浏览器、替人做决策。每多进入一个场景，"好"就多出一套定义。写代码的"好"是能运行、无缺陷、风格规范。陪聊天的"好"是有趣、不较真、令人愿意继续。做客服的"好"是耐心、不出错、不引发投诉。这三者之间不是程度差异，是方向差异。你无法用同一把尺子度量。

而且，如果你退后一步看，会发现一件之前从未发生过的事：软件从"匹配"变成了"创造"。搜索和推荐，本质上都是匹配——用户有一个需求，互联网上有一堆现成的内容，你的工作是把两边接上。接对了就是好，接错了就是差。大模型不是这样。它凭空生成一段给你，那东西在输出之前不存在于世界上任何地方。你没法用"找对了没有"来评价它，你只能问"这个东西本身好不好"。而这个问题，人类争论了几千年，从来没有过一个可操作的、共识性的答案。

用户关系也变了。搜索和推荐时代，用户是产品——他的注意力被卖给广告商，你优化的是参与度，点击、停留、时长，都可以精确计量。大模型时代，如果走订阅制，用户第一次变成了客户。客户为一段生成的文字付钱，他的满意是私人的、语境化的。你没法用一千万次点击的统计分布来代表一个人读完一段话时的感受。

成本结构也变了。搜索和推荐的边际成本几乎为零，广告收入覆盖了。大模型每一次推理都在烧 GPU，用户用得越多，你亏得越多——除非他付费。而 C 端广告那套逻辑在对话框里不成立，你没法在一段认真的回答中间插一条广告。"用户满意"和"赚到钱"之间那条自动的传导链，断了。

一个有上亿用户的 C 端大模型产品，它的 eval 体系、它的 A/B test，都在牵引模型朝一个方向迭代。但那个方向未必是“更强”。基模团队花三个月把数学推理能力拉高了一个台阶，送到 C 端产品上做 A/B test，留存跌了。回答变长了，语气变严肃了，用户觉得太像上课。一个在推理上更弱的模型，反而得分更高——因为它更短、更轻快、更像闲谈。C 端用户要的不是一个更聪明的模型，是一个更令人舒适的模型。推理能力在涨，用户满意度在跌。两条曲线朝相反的方向走。

再看另一边。多模态模型看起来离 AGI 更近——能看图、能听声、能操作屏幕，发布会上每一次演示都令人惊叹。但落到真实的 Vibe Coding 场景里，它的任务完成率可能不如一个更擅长蒸馏的模型。而 Vibe Coding，恰恰是大模型当前最能赚钱的方向之一。

最赚钱的方向，需要的不是最强的模型。最接近 AGI 的模型，未必是最能干活的那个。用户最满意的版本，可能是技术最弱的版本。"更好"这个词，在不同人嘴里指向完全不同的方向。

每一个场景都有自己的 eval，自己的指标，自己的“好”。榜单上那个“第一名”，不过是某一套定义下的第一名。换一个定义，座次重排。换一批用户，结论翻转。开头那三家公司同时宣布自己领先，不是失信，是“领先”这个词已经失去了统一的所指。评估工具在爆炸式增长，Benchmark 越来越多，eval 框架越来越精密，LLM-as-judge 将评估成本降低了数个量级，Chatbot Arena 让几十万用户直接投票。工具之丰富，远超以往任何时代。但工具解决的是"如何度量"的问题，解决不了"度量什么"的问题。你有一百把尺子，但没有人告诉你该取哪一把。

搜索时代不需要回答这个问题，因为专家替你选定了那把尺子，写在几百页手册里。推荐时代也不需要，因为用户行为自动选定了那把尺子——留存涨了，便是对了。大模型时代，没有人能替你选定。用户选不了，因为用户要的未必是“更好”。专家选不了，因为没有任何一个专家有资格替所有场景裁定“好”的含义。投资人选不了，因为他要的是增长叙事，不是质量判断。另一个模型也选不了，因为它的偏见与你的模型同样深，而你无法从系统内部察觉这种偏见。

这个圈子里有一句被反复引用的话：迭代是廉价的，方向是昂贵的。搭建一个能运行的系统很容易，难的是知道拿什么来衡量它的好坏。小帅此刻就坐在这个问题里。他设计了 eval，但他清楚那些维度是自行划定的。他跑了分数，分数涨了，但他无法确定那意味着模型变好了，还是 eval 本身变宽容了。他翻用户日志，看到 agent 写了一首关于飞行的诗，他不知道这算好还是算坏。不是因为缺一个更精密的指标，是因为没有任何人、任何文档、任何系统，有资格向他宣布答案。

在 TDD 时代，测试告诉他答案。在搜索时代，手册告诉他答案。在推荐时代，数据告诉他答案。如今没有人告诉他了。不是答案难以寻得，是这个问题第一次不再存在一个有资格作答的人。

## 1968 年的回声

1968 年那群人面对的局面，和今天有一个结构上的相似：不是某项技术不够强，而是整个行业缺少一套共同的工作方法。那时候所有人都在写代码，但没有人能回答“怎么让几百人协作的系统不崩溃”。后来给出的答案不是一项发明，而是一门学科。软件工程让几百万人有了共同的语言和纪律。

今天正在发生同样的事。

做 eval 的人，做 judge 校准的人，做 rubric 设计的人，做 agent 端到端回归的人——散落在不同公司、不同团队，用不同的工具。但他们做的事情本质上是同一件：先搞清楚这个系统到底在给谁用，然后想办法判断它用得够不够好，再让这个判断驱动下一步的改动。搞清楚为谁、判断好不好、驱动下一步——这件事在每一个团队里都在发生，只是没有人把它当作一门独立的学问来对待。

它值得被当作一门学问。不是 prompt engineering——那只是一个手段。不是 harness engineering 或 loop engineering——那只是一组工具。它关心的事情比这些都根本：AI 要落地为软件，就必须回答"为谁而建"和"如何知道建得好"，并且让后者持续驱动前者。无论基础模型还是 Agent，无论预训练还是应用层，这件事都绕不过去。

这门学科今天还没有教科书，没有共识，没有"这样做对、那样做错"的基本规范。每个团队都在各自摸索。但轮廓已经可以被辨认了。就像 1960 年代那些在混乱中坚持写测试的程序员，他们不知道自己正在"发明软件工程"，他们只是在力所能及的范围内试图让事情不那么混乱。今天做 eval 的人处境相同。学科不是被谁宣布成立的，它是一群人的实践慢慢凝结出来的。

但它一定会来。因为问题不会消失，而人不能永远在真空中迭代。

红灯不再变绿了。但路正在被走出来——关于这条路到底长什么样，且听下回分解。
